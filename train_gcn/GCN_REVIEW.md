# GCN 前沿策略复盘

## 结论

模型结构有贡献，但不是成功率从低到高的主要根因。

最终效果来自下面这条完整链路：

```text
正确的全局 35 m A* 真值
        +
训练与在线特征一致
        +
GCN 的拓扑编码和时间状态
        +
accepted route 保持、候选 witness 验证、碰撞检查
        +
原有 YOPO 控制器
```

其中最关键的变化是标签从“当前帧下一步怎么走”改成“从当前位置开始，提前 35 m 应该向哪一侧绕行”。如果标签仍然错误，仅仅加深 GCN 或增加隐藏层不能解决提前绕障问题。

## 最终部署的模型结构

当前线上使用：

```text
frontier_gcn_map2_35m.pt
input_dim = 20
architecture = legacy
```

这里的 `legacy` 不是旧的错误模型，而是当前部署检查点采用的结构名称。具体结构位于 [train.py](./train.py)：

1. 两层带边权的 `WeightedGCN`。
2. 每个节点保留自身特征，同时聚合拓扑邻居信息。
3. 对整张图做 mean pooling，得到当前图的全局上下文。
4. `GRUCell` 接收图上下文和上一帧的五方向选择，保持时间连续性。
5. 对五个虚拟候选节点分别打分，输出五个方向的 logits。

五个类别按从左到右排列为：

```text
column 0: 左前  +40 度
column 1: 左前  +20 度
column 2: 正前   0 度
column 3: 右前  -20 度
column 4: 右前  -40 度
```

在线 GCN 只输出 `0..4` 的方向列。它不生成轨迹、不替代 A*，也不直接判断碰撞；A*、witness 和下游碰撞检查仍然拥有最终决定权。

## 模型结构到底贡献了什么

### 有实际帮助的部分

**拓扑消息传递。**

候选方向不是独立的五个图像分类区域，而是连接到 skeleton graph 的虚拟节点。GCN 可以看到候选节点连接到哪一段拓扑、附近节点的度数、距离 mission goal 的关系以及图的整体形状。

**候选之间的共享表示。**

最终模型先编码整张图，再对五个候选方向分别打分。这样五个方向是在同一个图上下文中比较，而不是五个相互独立的分类器。

**时间状态。**

GRU 接收上一帧选择，降低左右方向在相邻帧之间来回跳变的概率。离线实验另外用验证集选择了 `0.05` 的方向切换惩罚，测试集从 `89.3%` 提升到 `91.3%`；这个数字是离线时序评估，不应直接等同于在线成功率。

### 不能归因于模型结构的部分

最终模型仍然是两层 GCN，而不是更深的 `strong`、`hybrid` 或 `joint` 结构。代码中虽然保留了这些实验结构，但当前 10/10 成功批次部署的是 `legacy` 检查点。因此不能说“加深网络后才成功”。

目前没有在同一数据集、同一训练划分、同一线上参数下对四种结构做严格消融，所以不能从现有日志计算出结构本身带来的独立百分点提升。现有证据更支持这样的判断：

> GCN 结构让拓扑和时间信息能够被利用；标签、特征一致性和执行链路修复决定了它是否学到了正确的行为。

## 为什么早期效果低

### 早期标签是局部的

早期数据主要基于当前 skeleton/局部图，目标接近当前帧的下一步方向。这会让模型在障碍物已经靠近时才改变方向，不能学习“提前很远绕开”。

### 早期类别严重不平衡

旧数据集的标签分布大致为：

```text
[13, 90, 1780, 110, 20]
```

模型输出正前方就能得到较高普通准确率，但左右绕行类别几乎没有学到。对应的一个旧模型测试结果约为：

```text
普通准确率       58.4%
Macro Accuracy  27.8%
相邻一列以内     96.0%
```

Macro Accuracy 低说明模型对少数方向类别不可靠，正是早期在线选择左右绕行不稳定的原因。

### 训练和在线输入曾经不完全一致

后续加入了 yaw、机体坐标下的节点位置、节点到 mission goal 的机体坐标等特征。最终输入是 20 维，训练和在线都使用同样的归一化、候选节点连接方式和列顺序。

如果标签是机体坐标系方向，而输入只有世界坐标，模型必须自己推断坐标变换，训练会明显变难。

## 真正有效的标签修复

最终标签由 [collect_privileged_dataset.py](./collect_privileged_dataset.py) 生成：

1. 使用完整的 Map2 静态点云，而不是某一帧的深度图。
2. 体素化并按无人机尺寸膨胀障碍物。
3. 从当前 odometry cell 到真实 mission goal 做普通 8 邻域 A*。
4. 取路径上至少 `35 m` 之后的点，而不是 `path[1]`。
5. 将该点转换为机体坐标系，并映射到五个方向列。
6. 没有完整可行 A* 路径的帧直接丢弃，不把不可达样本强行贴标签。

最终 Map2 数据集有 `5337` 个样本，标签分布为：

```text
[937, 1293, 1216, 1230, 661]
```

这个分布比早期数据平衡得多。最终静态地图标签的离线结果为：

```text
严格五分类准确率      89.3%
Macro Accuracy       89.4%
相邻一列以内          99.4%
原始 planner 匹配率   22.2%
```

这里的 `22.2%` 不是说原始 planner 不安全，而是说明原始 planner 的即时 frontier 选择与“静态全局地图 35 m 前瞻方向”不是同一个目标。

## 在线系统修复

模型准确率提高后，还需要让规划器正确使用 GCN 输出。关键修改如下。

### GCN 只替换 frontier 方向

GCN 变化不会清空当前已经验证过的 `accepted route`。它只是给下一次 frontier 搜索提供方向提示。

这避免了每次 GCN 从 column 1 变成 column 2 时，规划器都被迫立即丢弃正在执行的路线。

### 候选 witness 失败时保留 incumbent

新候选路线必须通过执行路径碰撞检查。如果候选失败，而原路线仍然可达且拓扑边仍然有效，则保留原路线，不发布空路线或错误的替代路线。

### accepted route 的安全预测采用连续确认

当前 accepted route 前方预测到不安全时，先累计证据；只有连续两帧确认不安全才强制重规划。单帧点云抖动不会立刻导致路线切换。

### 修正左右方向符号

统一了训练、GCN 节点、Graph frontier 排序和 RViz 箭头的列方向定义，保证 column 0 是左前、column 4 是右前。

### 保守的安全距离

最终稳定批次使用 `safe_distance=0.61 m`。之前试过 `0.4 m`，成功率反而下降，说明候选方向正确并不代表执行路线有足够的控制净空。

## SUPER 结果为什么不能直接反驳 GCN

后续使用：

```bash
STACK=scalenav_super bash scalenav_ws/src/aut_test/run_0_140_continuous.sh --count 10
```

时出现了 0/8 或更低的结果。这不能直接归因于 GCN，原因是 SUPER 使用了不同的执行器链：

1. 初始 SUPER 脚本把 Graph 的语义输入错误接成了用于 RViz 的 BGR 图，Graph 报告 `invalid contract: encoding=bgr8`，当时退化成 geometry-only。
2. 修复 topic 后，GCN 和语义候选确实正常工作，单架测试成功。
3. 批量 SUPER 仍出现 `OptimizationBakTrajInPolytopes failed`、backup trajectory 优化失败以及早期碰撞。

因此当前可以确认的是：

```text
GCN + 原有 Route-YOPO：最终 10/10
GCN + SUPER：主要暴露 SUPER 执行器/goal bridge/备份轨迹问题
```

两者不能混合解释。

## 最终判断

模型结构的作用是：

- 让候选方向读取拓扑邻域，而不是只看单点分数；
- 让五个方向在同一个图上下文中比较；
- 用 GRU 保留上一帧选择，减少方向抖动。

但成功率从早期低水平提升到最终 10/10，主要由以下三项共同决定：

1. **标签改为静态全局 A* 的 35 m 前瞻方向。**
2. **训练和在线的 20 维机体坐标特征完全一致。**
3. **GCN 只做 frontier proposal，原有 A*、witness、碰撞检查和路线保持继续生效。**

如果只替换模型结构、不修正这三项，不能期待相同的成功率。
